# ADR: 관측 데이터 수집 방식 — 애플리케이션 코드 계측 vs 배포 레벨 Java Agent

> 원본: Notion "관측 수집 방식 비교" (Infra > 작업목록, 모니터링). 작성: 인프라·배포 설계 담당, 2026-02-22.

- **상태**: 채택 (단기: Java Agent)
- **영향 범위**: gateway, users, stores, order, payment, order-query, checkins, coupon

## 배경
- 애플리케이션 코드를 가능한 한 수정하지 않고 Logs/Traces/Metrics를 모두 수집하고 싶다.
- 서비스별 OTel SDK 연동이 일관되지 않았고, 클러스터 수집 구조는 OTel Collector의 OTLP 수신 파이프라인 중심이라 서비스에서 OTLP export가 필요했다.
- 전 서비스를 빠르게 표준화하기 위해 배포 레벨(Java Agent) 방식을 우선 채택했다.

## 비교 기준
도입 속도, 운영 일관성, 비즈니스 컨텍스트 품질, 비즈니스 메트릭 확장성, 세밀한 제어(샘플링/마스킹/필터), 성능 최적화 유연성, 런타임 안정성, 보안/컴플라이언스.

## 옵션
**A. 애플리케이션 코드 계측 (OTel SDK/로깅 코드 내재화)**
- 장점: 도메인 이벤트·비즈니스 컨텍스트를 가장 정확히 반영, 커스텀 KPI 메트릭과 로그 스키마 통제 용이, 서비스별 정교한 샘플링/마스킹
- 단점: 서비스별 개발·리뷰·테스트·배포 필요로 느림, 팀별 구현 편차, 초기 전환 비용 큼

**B. 배포 레벨 Java Agent 주입 (채택)**
- 장점: 코드 수정 없이 전 서비스 공통 baseline, Helm/ArgoCD로 중앙 관리, HTTP/JDBC/Kafka 신호 단기간 확보
- 단점: 도메인 문맥 표현력 낮음, 자동 계측 카디널리티 관리 필요, Agent 다운로드/주입 실패 시 기동 리스크

| 항목 | 코드 계측 | Java Agent (현재) |
| --- | --- | --- |
| 도입 속도 | 느림 | 빠름 (Helm 값/템플릿 일괄 적용) |
| 운영 일관성 | 편차 발생 쉬움 | 중앙 통일 관리 |
| 비즈니스 컨텍스트 | 높음 | 중간 (HTTP/JDBC/Kafka 중심) |
| 비즈니스 메트릭 | 강함 | 약함~중간 |
| 세밀한 튜닝 | 강함 | 중간 (env 설정 중심) |
| 성능 최적화 | 직접 최적화 | 튜닝 폭 상대적으로 좁음 |
| 배포 안정성 | 런타임 의존 적음 | initContainer/agent 다운로드 실패 리스크 |
| 보안/컴플라이언스 | 코드 리뷰·정적 분석으로 통제 | 외부 다운로드·자동 캡처 범위 관리 필요 |

## 결정 및 로드맵
- **단기**: Java Agent로 전 서비스 Logs/Traces/Metrics baseline 확보
- **중기**: 결제·주문·체크인 등 핵심 도메인부터 코드 레벨 계측 병행
- **장기**: Agent 아티팩트를 외부 URL 대신 내부 저장소(S3/ECR)에 고정, 서비스별 관측 품질 SLO(필수 span/log field/metric) 정의

## 후속 결정 필요 사항
- Agent 공급 경로를 내부 고정 경로로 전환할지
- 서비스별 필수 관측 필드(orderId, paymentKey, userId 마스킹 정책) 표준
- dev/prod 샘플링 비율, 로그 레벨 정책 분리
